01 / DEPLOY

From checkout to first message in five minutes.

Hodhod runs on XAMPP, Apache, PHP, and MariaDB. The Windows launcher is a convenience; every step below works manually on Linux too. The application source is private, so this public guide assumes an authorized checkout.

Before you begin

  • PHP 8.1+ with PDO MySQL, mbstring, OpenSSL, and Argon2id.
  • MySQL 8 or MariaDB 10.4+ with utf8mb4.
  • Apache with mod_rewrite, mod_headers, and AllowOverride All.
  • Node.js 20+ and npm for the SPA build.

The Windows launcher expects the project at E:\xampp\htdocs\messanger.

  1. 1
    Configure

    Copy the example config, then set a random secret and your database credentials.

  2. 2
    Build

    Install the front-end dependencies and generate public/app.

  3. 3
    Launch

02 / MAP

The server is a relay. The browser holds the keys.

Hodhod keeps the content boundary in the client. The API authenticates, stores envelopes, coordinates membership, and serves ciphertext; it is not a decryption service.

01

Browser

React SPA plus Web Crypto. Identity keys, group keys, and plaintext stay here.

ECDH + AES-GCM
02

Transport

HTTPS carries ciphertext envelopes and the metadata required to route them.

TLS
03

PHP API

Auth, users, chats, messages, files, stream, and admin. Validates, authorizes, stores.

PHP 8.2
04

Data

MariaDB holds envelopes and metadata. Encrypted files live on disk.

HHF1 chunks

Encrypted in the browser

Every message gets a random AES-256-GCM key. Keys are wrapped with ephemeral ECDH P-256 and HKDF-SHA-256, then stored as opaque envelopes.

Files stay opaque

Files are split into 512 KiB plaintext chunks inside the HHF1 container. Each chunk is authenticated independently; the file key travels inside the encrypted message.

Metadata is visible

Membership, titles, timestamps, sizes, and activity are server-visible by design. That is the honest boundary of this threat model.

Request lifecycle and project map
  1. 01

    Apache routes the request through index.php and the API front controller.

  2. 02

    The PHP layer validates the session, CSRF token, device binding, rate limit, and membership.

  3. 03

    The database stores or returns ciphertext envelopes. The server never unwraps them.

  4. 04

    The browser verifies AAD bindings, unwraps the content key, and decrypts locally.

03 / SECURITY

Encrypted content. Honest metadata.

Messages and files are encrypted before they leave the browser. The server still sees who is talking, when, and how much. That is the trade-off, stated plainly.

Hodhod cryptographic layers
LayerDesign
Message contentAES-256-GCM with a random per-message key
Key agreementEphemeral ECDH P-256 + HKDF-SHA-256
Group keysRandom 256-bit key, wrapped per member, rotated on membership changes
Identity at restPBKDF2-SHA-256 + AES-256-GCM, 310,000 iterations
Portable backupPBKDF2-SHA-256 + AES-256-GCM, 600,000 iterations
LoginClient-side authHash, then Argon2id on the server
SessionsHTTP-only SameSite cookie, CSRF token, device binding
Audit statusAutomated tests only; no independent audit

The server can see

  • Usernames, profiles, roles, and account status.
  • Chat titles, membership, timestamps, and counts.
  • Ciphertext envelopes, sizes, IDs, replies, and reactions.
  • Encrypted file blobs, hashes, uploaders, and chat IDs.
  • Identity public keys, devices, sessions, and audit events.

The server cannot read

  • Message plaintext or file bytes.
  • Identity private keys or password KEKs.
  • Group keys in plaintext or unencrypted backups.
  • The contents of your recovery ceremony.
  • Anything the client never sends.
Not independently audited.

This is tested engineering, not a formal guarantee. Read SECURITY.md and LIMITATIONS.md before deploying for high-risk users.

Why ECDH instead of RSA?

Hodhod already uses a hybrid scheme: ephemeral ECDH derives key-wrapping keys, and AES-256-GCM protects content. RSA would also require a hybrid construction; RSA alone cannot encrypt arbitrary message bodies.

RSA-2048~112-bit

classical security. Larger keys and slower browser key generation.

RSA-4096~140-bit

classical security, but larger ciphertexts and no forward secrecy on its own.

ECDH P-256~128-bit

classical security, fresh ephemeral key per message, and a smaller browser footprint.

The current design is ECDH P-256 + HKDF-SHA-256 + AES-256-GCM. Static identity keys still mean no full forward secrecy; a future upgrade should use X25519, a double ratchet, and sender signatures.

Threat assumptions

Designed against

  • A curious or compromised application server or database.
  • Backup theft: database and storage.
  • Other users on the same deployment.
  • Network observers when served over HTTPS.

Not designed against

  • A compromised browser, OS, or XSS in the client.
  • A server operator serving modified JavaScript.
  • Traffic analysis or metadata correlation.
  • Coercion, key theft, or a compromised identity key.

04 / REFERENCE

A small API with a clear boundary.

The JSON API lives under /messanger/api. State-changing requests require the session's CSRF header; device-aware requests send a device ID. Encrypted content is validated as an envelope before it is stored.

Envelope rules

  • Bind cid, mid, and group version gv in AAD.
  • Never send plaintext content or file keys outside the envelope.
  • Reject mismatched IDs and key versions at decryption time.

05 / RUN

Hardening is part of the product.

A working install is not automatically a safe install. Treat secrets, storage, backups, and transport as production concerns from day one.

Key configuration values
KeyPurpose
app.envdevelopment or production; use production on a server
app.secretServer-side hashing secret; use a random 64-hex value
app.max_upload_bytesServer-side encrypted upload ceiling
app.storage_dirEncrypted file storage directory
db.*Database host, port, name, credentials, and schema path
security.*Argon2id cost, login attempts, lockout, and welcome text
limits.*Per-scope rate limits for auth, send, read, poll, admin, upload, and download
Production mode

Set app.env to production and replace app.secret with a fresh 64-hex value.

Dedicated database user

Never run the app as root. Restrict network access to MySQL.

HTTPS and HSTS

Serve only over TLS. Add HSTS at the web server or reverse proxy.

Upload limits

Match post_max_size and upload_max_filesize to the intended file ceiling.

Blocked source paths

Keep config/, server/, storage/, tests/, web/, and .git* inaccessible.

Backups

Back up both the database and storage/files. Protect both as sensitive data.

Redis discipline

Leave Redis disabled unless it is reachable; otherwise requests may pay a timeout.

Disposable tests

Run live API tests only against a disposable development database.

Metadata is not encrypted.

Hodhod protects content. It does not hide chat membership, timestamps, message sizes, or activity from the server operator.

07 / BOUNDARIES

What Hodhod does not protect.

Security claims are only useful when they include the edges. These are the edges you need to understand before deployment.

Metadata

The server sees who talks to whom, when, membership, sizes, and activity.

No full forward secrecy

Static identity keys mean identity-key compromise can expose historical envelopes. A ratchet is future work.

No sender signatures

Messages are not cryptographically signed by the sender; room membership is the trust boundary.

Client compromise

XSS, a compromised browser, or a malicious JavaScript build can expose plaintext.

No independent audit

The cryptography and implementation are tested engineering, not a formal guarantee.

Recovery is final

Losing the encrypted identity backup can make historical ciphertext unrecoverable.
